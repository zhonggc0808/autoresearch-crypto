# LLM Research Contract

> Defines the rights, boundaries, and responsibilities of LLM agents operating
> within the autoresearch-crypto research loop.
>
> **Version:** v0.6.5 (End-to-End Cycle Acceptance)
> **Last updated:** 2026-06-15
> **Status:** ✅ Ratified

---

## 1. Purpose

This contract answers two questions that every LLM agent must be able to answer
before taking any action:

1. **What can I modify?** — The allowed workspace.
2. **What results qualify a candidate for promotion?** — The gates.

Violations of this contract (direct file writes outside the allowed workspace,
modification of oracle evaluation logic, baseline tampering) are grounds for
immediate rejection of the agent's output.

## 3. Allowed Workspace

> **Note on scope:** The rules below apply to **LLM research agents** operating
> within the automated research loop. Human maintainers and infrastructure agents
> (e.g., implementing new scripts, updating the contract, maintaining the oracle)
> retain full write access to `scripts/` and `docs/`. The boundary is about *who
> or what is acting* — not about technical file permissions.

LLM agents may create, modify, and delete files **only** within:

```
research_workspace/
├── llm_candidates/      # Candidate spec JSONs (generated by agent)
├── llm_scorecards/      # Evaluation scorecards (produced by score_candidate.py)
├── proposals/           # Research proposals (.md)
├── notes/               # Free-form observations (.md)
└── llm_results.tsv      # Experiment tracking log
```

### 3.1 File Type Restrictions

| Directory | Allowed extensions | Restrictions |
|-----------|-------------------|--------------|
| `llm_candidates/` | `.json` | Must pass schema validation (see §4.4) |
| `llm_scorecards/` | `.json` | Generated by `score_candidate.py` only |
| `proposals/` | `.md` | Must follow `_TEMPLATE.md` format |
| `notes/` | `.md` | Free-form, no restriction |
| `llm_results.tsv` | `.tsv` | Appended by `score_candidate.py` only |

### 3.2 What Agents CANNOT Do Even Inside Workspace

- ❌ Modify oracle output files (`oracle_report.json`, `experiments.jsonl`, `results.tsv`)
- ❌ Modify baseline files in `baselines/`
- ❌ Execute arbitrary Python code — only approved scripts via `uv run`
- ❌ Delete or overwrite other agents' candidates without documented rationale
- ❌ Create Python files (`.py`) in any directory (see §3.3)

### 3.3 Code Generation Exception

LLM agents may NOT create or modify `.py` files in this phase. Python strategy
variants require:
1. A proposal in `proposals/`
2. Human approval
3. Human creates the `.py` file

This restriction is relaxed only when v0.9 (Limited Code Generation Sandbox) is
active and the code is written to `research_workspace/llm_code_candidates/`.

## 4. Validation Framework

### 4.1 Data & Split

| Property | Value |
|----------|-------|
| Symbol | ETHUSDT |
| Interval | 5m |
| Dataset | `ETHUSDT_5m_1300d.parquet` (~374K bars, 2022-11 to 2026-06) |
| Split | Fixed 70/30 (IS: ~262K bars, OOS: ~112K bars) |
| Regime filter default | EMA fast=50d, slow=200d |

**Data source** (`scripts/research_oracle.py:75-93`): The oracle loads from
`data/crypto/ETHUSDT_5m_1300d.parquet` exclusively. No fallback to shorter data.

### 4.2 Evaluation Modes

Each candidate is evaluated in three signal modes (see `research_oracle.py:692-698`):

1. **Raw** — Direct strategy signals, no transformation
2. **Safe-execution** — Same-bar reversals converted to close→confirm→open
3. **Regime-permission** — Short positions blocked in BULL regime

### 4.3 Metrics Produced

All metrics come from `StrategyEvaluator` in `dex/strategies/base.py`:

| Metric | Source | Notes |
|--------|--------|-------|
| `return` | `StrategyEvaluator.evaluate()` | Total return over period |
| `dd` (max drawdown) | `StrategyEvaluator.evaluate()` | Peak-to-trough |
| `sharpe` | `StrategyEvaluator.evaluate()` | Annualized Sharpe ratio |
| `win_rate` | `StrategyEvaluator.evaluate()` | Fraction of winning trades |
| `annual_return` | `StrategyEvaluator.evaluate()` | Annualized return |
| `annual_vol` | `StrategyEvaluator.evaluate()` | Annualized volatility |
| `trades` | Trade log count | Number of closed trades |
| `trades_per_year` | Computed from trades/bars | Normalized annual trade count |
| `rolling_6m_min_return` | `_compute_rolling_metrics()` | Worst 6-month rolling window |
| `rolling_12m_min_return` | `_compute_rolling_metrics()` | Worst 12-month rolling window |
| `execution_parity` | `_compute_execution_parity()` | Equity curve correlation: raw vs safe |
| `fee_sensitivity` | `_compute_fee_sensitivity()` | Return at 0/2/4/10 bps fees |
| `corr_vs_baseline` | `_compute_equity_correlation()` | Equity correlation vs v2.1 baseline |

### 4.4 Candidate Schema (v0.1)

A valid candidate JSON must contain:

```json
{
  "experiment_id": "exp_NNNN",
  "parent_id": null,
  "candidate_role": "standalone",
  "strategy": "channel_breakout",
  "description": "Hypothesis for this experiment",

  "params": {
    "strategy_type": "regime_permission_channel_breakout",
    "regime_change_policy": "permission_based",
    "regime_filter": { "fast_days": 50, "slow_days": 200 },
    "bull": {
      "candidate": "...",
      "strategy_params": { "entry_lookback": 375, "min_hold_bars": 432 },
      "permission": { "allow_long": true, "allow_short": false, ... }
    },
    "bear": { ... },
    "neutral": { ... }
  }
}
```

**Validation rules** (enforced by `build_candidate_from_spec.py`):
- `experiment_id` must be unique and sequential (`exp_NNNN`)
- `strategy` must be a registered family (`channel_breakout` — Phase 0.8 expands)
- `candidate_role` must be one of: `standalone`, `filter`, `overlay`, `ensemble_component`
- `params.strategy_type` must match a known strategy type
- `entry_lookback` must be int in [20, 1000]
- `min_hold_bars` must be int in [12, 1440]
- All regime subsections (bull/bear/neutral) must be present for standalone candidates
- `fast_days` must be < `slow_days`
- No field may reference live/demo paths, oracle modification, or unrestricted search

## 5. Candidate Status Rules & Promotion Gates

### 5.1 Status Values

| Status | Meaning |
|--------|---------|
| `BASELINE` | Frozen v2.1 baseline or known-risk run (never disqualified) |
| `REJECT` | Automatic disqualification triggered (DD_OVER_50 or ROLLING_NEGATIVE) |
| `WARN` | Passed disqualification gates, but one or more warnings active |
| `PASS` | No disqualifications, no warnings |

### 5.2 Disqualifications (Hard Reject)

| Flag | Condition |
|------|-----------|
| `DD_OVER_50` | IS drawdown < -50% OR OOS drawdown < -50% |
| `ROLLING_NEGATIVE` | 6-month rolling minimum return < 0 |

These are defined in `research_oracle.py:549-553`.

### 5.3 Warnings (Soft Flags)

| Warning | Condition |
|---------|-----------|
| `DD_OVER_40` | IS drawdown < -40% |
| `TRADES_UNDER_30` | IS total trades < 30 |
| `OOS_DEGRADE` | OOS return < 50% of IS return |
| `EXEC_PARITY_LOW` | Execution parity < 0.85 |
| `CORR_BASELINE_099` | Equity correlation with baseline ≥ 0.99 |
| `FEE_FRAGILE` | Return negative at 10bp fees (OOS or IS) |

These are defined in `research_oracle.py:556-570`.

### 5.4 Promotion Gates (for `promote_review`)

**Standalone candidates** — ALL must pass:

| # | Gate | Source |
|---|------|--------|
| 1 | Oracle status == PASS, no disqualifications | `flags.status` |
| 2 | Safe execution parity >= 0.90 | `execution_parity` |
| 3 | Rolling 12-month minimum return > 0 | `rolling.12m_min_return` |
| 4 | IS drawdown >= -40% | `is.raw.dd` |
| 5 | Correlation vs v2.1 baseline < 0.95 | `correlation.vs_baseline` |
| 6 | Return stays positive at 10bp fees | `sensitivity.is.fees.10bp` > 0 |
| 7 | Trade count >= 20 per year | `is.raw.trades_per_year` |
| 8 | Human reviewed and approved | Manual gate |

**Filter/Overlay candidates** — see `research_workspace/README.md` for
separate rules. Filter/overlay candidates do not need to be profitable alone.

### 5.5 Verdict Rules (v0.3)

The verdict engine is a dual-window state machine. Each candidate progresses
through validation stages, with clear terminal and non-terminal states.

#### State Machine

```
candidate_created
  └→ [validate schema]
       ├→ invalid_candidate ───────────────── STOP
       └→ [1300d oracle]
            ├→ kill (1300d REJECT/disqualifications) ── STOP
            └→ requires_2600d (1300d PASS/WARN)
                 ├→ [2600d data check]
                 │    └→ blocked_missing_2600d_data ──── STOP
                 └→ [2600d oracle]
                      ├→ research_only_recent_regime ─── STOP
                      └→ promote_review_pending ──────── STOP
```

#### Verdict Enumeration

| Verdict | Meaning | Terminal |
|---------|---------|----------|
| `kill` | Disqualified at 1300d | ✅ Yes |
| `requires_2600d` | 1300d passed, 2600d required | ❌ No |
| `blocked_missing_2600d_data` | 2600d dataset not available | ✅ Yes |
| `research_only_recent_regime` | Passed 1300d, failed 2600d | ✅ Yes |
| `promote_review_pending` | Both windows clear, human review needed | ✅ Yes |
| `invalid_oracle_output` | Oracle result unreadable | ✅ Yes |
| `invalid_candidate` | Candidate schema violation | ✅ Yes |

#### 1300d Verdict Mapping

| Oracle Status | Verdict |
|---------------|---------|
| REJECT (with disqualifications) | `kill` |
| WARN | `requires_2600d` |
| PASS | `requires_2600d` |
| BASELINE | `kill` |

#### 2600d Verdict Mapping

| Oracle Status | Verdict |
|---------------|---------|
| REJECT (with disqualifications) | `research_only_recent_regime` |
| WARN | `research_only_recent_regime` |
| PASS | `promote_review_pending` |
| BASELINE | `research_only_recent_regime` |

#### Architecture: Scorer vs Orchestrator

- **`score_candidate.py`** — Pure scorer. Takes `(oracle_result, stage)` → structured
  scorecard with verdict + promotion gates. No orchestration logic.
- **`evaluate_candidate.py`** — State machine orchestrator. Manages the lifecycle,
  calls oracle for each stage, delegates scoring to `score_candidate.py`, tracks
  state transitions in evaluation history JSON.

This separation ensures the scoring logic remains testable and the orchestration
can be replayed/audited via the evaluation state files.

#### 2600d Availability

2600d evaluation is **blocked** until `ETHUSDT_5m_2600d.parquet` exists in
`data/crypto/`. The orchestrator detects this via `_has_2600d_data()` and
returns `blocked_missing_2600d_data` without attempting to run the oracle.
No candidate can be promoted through the full dual-window pipeline until
2600d data is available.

## 7. Change Process

This contract is version-controlled in `docs/llm_research_contract.md`. Changes
require:

1. A proposal in `research_workspace/proposals/` explaining the rationale
2. Human review and approval
3. Version bump and changelog entry

LLM agents may propose contract changes in `proposals/` but may not modify this
file directly.
